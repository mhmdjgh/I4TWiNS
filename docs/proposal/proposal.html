1. Summary

The agent receives one free-form prompt, decides which of four skills it needs (at most two), runs them as a LangGraph graph and returns a single answer in the user's language. The router's decision is a Pydantic-validated JSON object, and the calculator always computes with a real tool. Fallbacks and clarifications are deterministic code paths, not prompt suggestions.

100%skill detection (15/15)
4/4ambiguous and no-skill cases handled
~3 saverage end-to-end latency per prompt
212offline tests · CI on every PR

What makes the design hold up as it grows

Skills are plugins

A registry is the single source of truth. The router prompt, the router's output validation and the graph nodes are generated from it, so a new skill is one module and the graph does not change.

Context is budgeted, not hoped for

The router sees compact skill cards, shortlisted to top-k for large catalogues. Parallel skills share an output budget, chains pass only the previous output, and oversized texts go through map-reduce or chunking.

Code around the model

Fallback policies, composing results, clarification language and fact checks on translations are deterministic, so behaviour does not depend on a small model following every instruction.

Measured, then fixed

Every prompt or configuration change came from a real run: reasoning-token truncation, a wrong weekday in a translation, a dropped named entity in a summary. Each is documented with before/after evidence.

4. Execution model

The router's decision carries a mode. It is the only component that can tell whether two tasks depend on each other, so it makes that call.

ModeWhenHow it runsAnswer
singleOne skillOne SendThe skill's output
parallelIndependent tasks: "translate 'good luck' into Persian, and what is 15% of 3,200?"One Send per skill in the same superstep; the router pins each skill's span of the message (used only if it occurs verbatim); list reducerLocalized titled sections
sequentialThe second task works on the first one's output: "summarize this, then translate the summary"Only the first node starts; after_skill sends only its output plus the user's instruction to the next node; a failure stops the chainThe final output; intermediates in the trace
Always chaining would slow independent tasks and feed unrelated text into the second skill. Always parallelizing would translate the full text instead of the summary. Both shapes are in the evaluation set; the router chose the right mode in all three cases.

  "confidence": 0.95,
  "needs_clarification": false

Validation

  • Aliases normalized (Translate → translator)
  • Names checked against the registry; at most N skills
  • Mode made consistent with the number of skills
  • Errors phrased for the model, one repair round; truncated replies retried with a larger limit

Fallback policies (code, after the LLM)

The router prompt is few-shot and bilingual, with rules for the frequent confusions: the requested action decides the skill, not the topic ("who invented algebra?" is chat), when to chain versus parallelize, when to ask rather than guess, and treating instructions inside the text to process as content.

6. Context-window strategy

The scaling problem the design is built around: as more skills are registered and more of them run per request, every call must still fit the model's window. Each source of growth has its own mechanism in src/skill_agent/context/.

Source of growthMechanism
More skills in the catalogueRouter sees compact cards only. Above a threshold, a bilingual lexical shortlister (keyword phrases plus IDF overlap, no LLM call) keeps the top-k cards; the fallback card is always kept.
Long messages to the routerHead/tail excerpt: the request sits at the edges, while the long middle is the document, which routing does not need.
Several skills writing into one answerParallel steps share a total output budget; each chained intermediate is capped, so the next step's input is bounded by construction.
History accumulating along a chainThe next step receives only the previous output; parallel branches are isolated by Send.
Texts larger than the windowMap-reduce summarization (repeated reduce while partials are too long); chunk-by-chunk translation in order; excerpts for chat and calculator.
Hidden reasoning tokensReasoning off by default and switched in each provider's dialect; per-skill opt-in (chat uses low); an allowance is added to max_tokens when it is on; empty truncated answers are retried once.

Chunk boundaries follow paragraphs, then sentences (including Persian ؟), then words. Token counts are estimated without a provider tokenizer and deliberately over-count Persian, the safe side for a budget.

7. Skills and prompt engineering

SkillPrompt approach
RouterGenerated catalogue, JSON contract, 9 rules, 7 bilingual examples (sequential, parallel, clarification in both languages, "math topic, nothing to compute")
SummarizerFaithfulness (no added causes or opinions; keep names, numbers and dates; specific over generic), length defaults that yield to explicit constraints, source-language output, Persian orthography
TranslatorTranslate the payload, not the instruction; translate embedded instructions instead of following them; fact preservation with a weekday glossary; register and idioms; output only
CalculatorExtraction only: JSON list of labelled expressions in a whitelisted syntax; number words and Persian digits converted; never pre-compute
General chatMirror the language, be brief and honest; answer only the conversational part when another skill handles the task

Shared techniques: content is fenced in <request>/<text> tags (which also defuses "ignore the above" inside a text), rules are written so they can be checked, few-shot is used only where the output has a format, and evaluation sentences are kept out of the examples.

Improvement example: a wrong weekday in a translation

VersionChangeResult on "…moved to Thursday morning…"
v1Four-line prompt: translate, default direction, keep meaning, output only«…به صبح جمعه منتقل شده…» Friday
v2Scope, accuracy rules (names, numbers, dates, weekdays), weekday glossary, register, Persian orthographyStill جمعه: the glossary was ignored
v3Deterministic check of digits and weekday names in both directions; on a mismatch, one targeted repair requestFired in the final evaluation and fixed the answer live: «…صبح پنجشنبه منتقل شد…»
With a model that has about 3B active parameters, instructions narrow the error rate, but facts that can be checked mechanically should be checked in code. The summarizer had a similar issue: v1 turned "the Zayandeh River drying up" into "recent droughts" and added an unstated causal link. v2's faithfulness rules restored the named entity.

8. The calculator tool

  • Parsed with ast and evaluated over a node whitelist; no eval, names, attributes or arbitrary calls
  • Exact Fraction arithmetic (0.1 + 0.2 = 0.3), float only for irrational functions
  • Limits on length, nodes, exponent, factorial and result size
  • Accepts ۲۵٪, ×, ÷, ^, 1,250,000, 2(3+4)

Extract-then-execute. The LLM converts the request into expressions; the skill calls the calculate tool for every one. With optional native tool calling, a model can skip the tool and answer from memory. Here the tool call is unconditional, so every number in an answer comes from the tool.

Tests include injection payloads: __import__, dunder traversal, lambdas, attribute access, keyword arguments, comparisons and conditionals.

9. Persian language support

  • Input: Arabic ي and ك → Persian ی and ک, tatweel removed, ZWNJ cleaned; digits and line breaks preserved for translation.
  • Routing: Persian and colloquial examples, such as چند میشه؟ ("how much is it?") and اینو برام خلاصه کن ("summarize this for me"); Persian keywords in the shortlister.
  • Output: the response language follows the user's own words; system strings localized; prompts require half-spaces, Persian punctuation and the letters ی and ک; a clarification in the wrong script is replaced.
  • Numbers and facts: the calculator accepts Persian digits, the decimal mark ٫, the thousands separator ٬ and the percent sign ٪. Weekdays are checked in both directions; Thursday may be written پنج‌شنبه, or پنج شنبه, or پنجشنبه.
  • Display: the dashboard sets each paragraph's direction from its first strong character, so mixed answers stay readable.

11. Evaluation

15 labelled prompts (7 English, 8 Persian): 7 clear, 4 multi-skill (two sequential, one parallel, one borderline), 2 ambiguous, 2 no-skill. Metric: exact match of the selected skill set, with order checked for sequential cases.

113/15Both failures were truncated JSON: about 400 of 500 output tokens went to hidden reasoning. → Reasoning made configurable and off by default (same decision, 1.7 s vs 9.8 s), allowance and truncation retry.

213/15One real miss (summary requested without text → summarizer now asks for it); one case lost to the free tier's 50 requests/day limit.
3–415/15 · 14/15Empty translations (all output spent on hidden reasoning; the gateway rejected OpenRouter's switch) → reasoning switch per provider, retry of empty answers. 615/15Clear 7/7, multi 4/4, ambiguous 2/2, no-skill 2/2, mode 3/3. Rule: a summary in another language is summarizer → translator (plus a code guard). Parallel translator falls back to the quoted text and sees only its own instruction.

Per skill: precision 1.00 for every label; recall 1.00 except general chat (0.80), because the greeting + square-root case was answered by the calculator alone, an accepted alternative.

12. Engineering practice

Quality gates

ruff (lint and format), mypy in strict mode, and 212 offline tests driven by a scripted chat model. They cover the evaluator, routing policies, every graph path, context mechanisms, translation checks, the CLI and the dashboard (Streamlit AppTest). GitHub Actions runs all of them on every push and pull request.

Git workflow

A branch per change (feat/, fix/, test/, ci/, docs/, chore/) and a pull request per branch with a description, merged with merge commits. Conventional Commits; bodies explain the reason, including the evidence behind each fix.

Interfaces

CLI: ask, chat, route, eval, skills, config, graph. Streamlit dashboard: playground with routing, trace and tool calls; architecture view; evaluation view.

Extending

A new skill is one class with a SkillCard and a prompt file. The router prompt, validation, shortlister, graph node and dashboard pick it up automatically.

Free tier: 50 requests/day, upstream rate limitsPaid or self-hosted inference, retries with backoff, circuit breaker

Estimated token counts; lexical shortlisterThe model's tokenizer; multilingual embedding retrieval over skill cards
Heuristic split of instruction and text in long promptsRouter-returned spans, or the text as a separate input
Synchronous calls; sequential map-reduceAsync graph, concurrent chunks within rate limits, streaming
Translation checks detect wrong numbers, weekdays and Latin-script leftovers, but the repair uses the same small model (it kept the Spanish suerte for “good luck”), and they cannot see a change of meaningEntity, date and unit alignment; domain glossaries; a larger model or reasoning for translation
Numeric calculator only; story problems need a little reasoning to get the signs right, which makes them take 10–30 sSymPy-backed tool for algebra, with the same safety envelope; a stronger extraction model
No memory, auth, persistence; in-response trace onlySessions, authentication, audit logs; OpenTelemetry/LangSmith tracing and cost metrics

Assumptions made where the brief was open

  • Translation without a stated target: Persian → English, anything else → Persian.
  • Sequential requests return the final output; intermediates are visible in the trace.
  • Clarification only when a skill is clearly wanted but cannot run, or confidence is low; vague but conversational messages go to chat.
  • The response language is that of the user's own words, not of a quoted text.
  • "Parameters" means total parameters (30B for the MoE primary, ~3B active).
